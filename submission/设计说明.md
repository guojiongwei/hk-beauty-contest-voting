# 数据库与 API 设计思路

## 一、数据库设计

### 1. 表结构（4 张表）

| 表 | 作用 |
| --- | --- |
| users | 投票人账号，用户名、手机号唯一 |
| candidates | 候选人资料 |
| votes | 投票记录，用户与候选人多对多 |
| verification_codes | 注册手机验证码，支撑“手机号验证”要求 |

### 2. 业务覆盖

- 注册需要手机号验证，因此验证码不能放在 users 表：未注册成功的手机号没有用户记录，且同一手机号会有多次获取记录，需要保留历史用于限流与审计，所以独立成表；
- 投票关系用 votes 表表达，而不是在 users 上存 `candidate_id`，因为需求未限制只能投一人，用关联表才能正确表达“多对多”，也便于后续统计票数；
- 验证码记录 `purpose` 字段，当前只使用 `register`，为登录、找回密码等场景预留扩展位，避免后续加表或改表。

### 3. 列类型与 NULL

- 主键统一 `bigint`；手机号、用户名、摘要、URL 使用 `varchar`，简介使用 `text`（长度不可预估）；
- 手机号用 `varchar(20)` 而不是整数：可能包含国家码或前导 0，且不参与运算；
- `password_digest`、`code_digest` 用 `varchar(100)`：bcrypt 输出固定 60 字符，留出算法升级余量；
- 业务必需字段一律 `NOT NULL` 并给默认值（如 `purpose default 'register'`、`attempts default 0`），把数据完整性交给数据库；
- 只有“确实可能为空”的字段才允许 NULL：`candidates.description`、`photo_url` 允许运营后补资料；`verification_codes.used_at` 用 NULL 表示“未使用”，比额外布尔字段更省空间且不会自相矛盾。

### 4. 索引

- `users.username`、`users.phone_number` 唯一索引：既支持登录查询，也在数据库层杜绝重复注册；
- `votes (user_id, candidate_id)` 联合唯一索引：防刷票的最终防线，同时支撑“查询某用户已投候选人”；
- `votes.user_id`、`votes.candidate_id` 外键索引：支持按用户/候选人统计；
- `verification_codes (phone_number, purpose, created_at)`：取最新验证码与 60 秒限流判断都走该索引；
- `verification_codes.expires_at`：供定时任务清理过期数据；
- 手机号在验证码表不建唯一索引，因为一个手机号必然有多条历史记录。

## 二、REST API 设计

### 1. 接口与资源路径

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /api/v1/verification_codes | 发送注册验证码 |
| POST | /api/v1/users | 注册（携带验证码） |
| POST | /api/v1/sessions | 登录，返回 JWT |
| DELETE | /api/v1/sessions/current | 登出 |
| GET | /api/v1/candidates | 候选人列表（分页，含 has_voted） |
| GET | /api/v1/candidates/:id | 候选人详情（含 has_voted） |
| POST | /api/v1/votes | 投票 |

路径全部以名词资源为中心，用 HTTP 方法表达动作：注册是创建用户用 POST /users，登录是创建会话用 POST /sessions，登出是删除当前会话用 DELETE /sessions/current，投票是创建投票记录用 POST /votes，避免出现 `/getCandidates`、`/doVote` 这类动词路径。

### 2. 认证与会话

- 登录成功返回 JWT，前端在 `Authorization: Bearer <token>` 中携带；服务端无状态，不建会话表；
- 登出对无状态 JWT 而言没有服务端副作用，因此返回 200 由前端删除 Token，即使 Token 已过期也允许调用，保证退出流程不被阻塞；
- 候选人列表、详情、投票均需登录，投票人 `user_id` 一律取自 Token，不接受前端传入。

### 3. 手机号验证

- `POST /verification_codes` 生成 6 位数字验证码，bcrypt 摘要入库，5 分钟过期；
- 同一手机号 60 秒内重复发送返回 429，最多输错 5 次，使用后立即失效；
- 注册时先校验验证码、再创建用户，用户创建成功后才标记验证码已使用，避免用户信息校验失败白白作废验证码；
- 生产环境通过短信服务商下发，明文不落库；仅开发环境在响应中返回 `debug_code` 便于联调。

### 4. 分页与投票状态

- 列表支持 `page`（默认 1）与 `per_page`（默认 10、上限 50），按主键升序保证翻页稳定；
- 响应使用 `data` + `meta` 分离：`meta` 包含 `current_page`、`per_page`、`total_count`、`total_pages`、`has_next`、`has_prev`；
- `has_voted` 用 `current_user.votes.pluck(:candidate_id)` 一次性取出后内存判断，列表固定 2 条查询，避免 N+1。

### 5. JSON 结构

- 成功：`{ "data": ..., "message": "..." }`；列表额外带 `meta`；登录返回 `token` 与 `user`；
- 失败：统一 `{ "error": "错误描述" }`，不返回 Rails 默认 HTML 错误页；
- 状态码语义：201 创建成功（注册、投票、发送验证码）、200 查询/登录/登出、401 未认证、404 资源不存在、422 参数或业务校验失败、429 发送过于频繁、500 服务端异常；
- 任何响应都不返回 `password_digest` 与验证码摘要。

### 6. 防刷票

三层防护：数据库联合唯一索引作为最终防线；模型 `uniqueness` 校验提供友好提示；控制器捕获 `ActiveRecord::RecordNotUnique` 处理并发请求，统一返回 422「您已经投过票了」。
